# 4.2 Learning & Adaptation（Ch.9）

> Agent 从经验中学习，动态调整行为

---

## 一、行业调研

### 核心问题

4.1 解决了"Agent 记住用户是谁"，但还有一个更深层的需求：

> **Agent 的"行为"本身能不能进化？**

- 用户连续 5 次纠正"邮件写轻松点"，Agent 应该自动学会以后都用轻松语气
- Agent 执行任务失败了，下次遇到类似任务应该避免同样的错误
- 这不是"记住事实"，而是"学会做法"——即 **Procedural Memory 的动态自更新**

### 记忆 vs 学习

| 维度 | 4.1 Memory | 4.2 Learning |
|---|---|---|
| 记什么 | **事实**（"用户叫小王"） | **行为规则**（"回复要简洁"） |
| 存哪里 | Semantic Memory | **Procedural Memory**（指令/规则） |
| 触发方式 | 被动积累（用户说什么记什么） | **主动反思**（从成功/失败中提炼策略） |
| 技术手段 | Mem0.add() 提取事实 | Agent 自己改写 system prompt / 规则库 |
| 主体 | 记住"用户是怎样的人" | 记住"我应该怎么做" |

---

### 行业三大落地方式

#### 方式 1：从用户反馈中学习（Feedback → Procedural Memory Update）

**场景**：用户对 Agent 的输出做了修改/纠正，Agent 从修改中推断偏好并更新自身行为。

**工作流**：
```
用户反馈（编辑邮件/说"太正式了"）
    → Agent 反思："用户偏好非正式语气"
    → 更新存储的指令：preferences.tone = "casual"
    → 下次写邮件自动用轻松语气
```

**生产代表**：
- **LangGraph langmem SDK**：提供 `create_manage_memory_tool` 让 Agent 在 Hot Path 中主动存规则；`prompt_optimizer` 基于反馈自动优化指令
- **Claude Code Auto-memory**：Agent 工作中发现有用信息（debug 模式、构建命令、偏好）自动写入 `MEMORY.md`，下次会话自动加载
- **FareedKhan/langgraph-long-memory**（GitHub）：Email Agent 从用户编辑中学习偏好，通过 Memory Manager LLM 安全更新规则（严格"只追加不覆盖"）

**关键设计**：
- Memory Manager LLM 专门负责"怎么更新"，主 Agent LLM 只负责"怎么执行"
- 更新规则必须有安全约束：**只追加不覆盖**、不删除已有偏好、有冲突时保留最新

#### 方式 2：任务后反思提炼 Heuristics（ERL — Experiential Reflective Learning）

**场景**：Agent 执行完一个任务（成功或失败），通过 LLM 反思提炼"下次该怎么做"的规则。

**工作流**：
```
任务执行 → 获取结果（成功/失败）
    → LLM 反思 trajectory："这次成功因为先搜索再回答"
    → 提炼为 Trigger-Action 规则：
      "IF 用户问事实性问题 THEN 先搜索再回答"
    → 存入 Heuristic Pool（向量化存储）
    → 新任务开始前：检索 Top-20 相关规则 → 注入 prompt
```

**核心论文**：[ERL（arXiv:2603.24639, 2026.03）](https://arxiv.org/abs/2603.24639)
- **GAIA2 基准**：成功率 56.1%，比 ReAct baseline +7.8%，超过 ExpeL 和 AutoGuide
- **关键发现**：原始 trajectory 作为 few-shot **反而降低性能（-1.9%）**！噪声太多。提炼后的 heuristic 才有效
- **检索方式**：LLM-based ranking > 纯 embedding 相似度（LLM 能考虑多样性和信息量）
- **最优 k=20**：注入 20 条最相关规则到 prompt
- **单次即可学习**：不需要反复试错，一次执行就能提炼有效经验
- **成本**：增加约 40% API 调用（反思 + 检索步骤）

**对比 ExpeL / AutoGuide**：
| 方法 | 学习粒度 | 需要多次尝试？ | 检索方式 |
|---|---|---|---|
| Raw Few-shot | 整条 trajectory | 否 | 纯拼接 |
| ExpeL | 跨任务聚合规则 | 是 | 嵌入 |
| AutoGuide | 状态级别规则 | 是 | 状态匹配 |
| **ERL** | 单任务结构化 heuristic | **否（单次）** | **LLM 排序** |

#### 方式 3：Prompt 自动优化（Self-Optimizing Prompt）

**场景**：累积足够的失败案例后，自动分析失败模式并改写 system prompt。

**工作流**：
```
累积失败案例（eval 未通过的对话）
    → LLM 分析失败原因
    → 生成 Natural Language Gradient（文本梯度 = "为什么这个 prompt 失败"）
    → 基于梯度改写 system prompt
    → 部署新 prompt → 观测效果 → 迭代
```

**生产代表**：
- **DSPy / ProTeGi**：读失败对话 → 生成文本梯度（像 PR review 一样的批评）→ 改写 prompt
- **SuperOpt（2025.12 论文）**：把"整个环境"作为优化目标（prompt + tools + memory schema + 验证逻辑），模型本身冻结不动
- **agent-opt**：提供 6 种算法，ProTeGi（prompt 改写）、BayesianSearch（few-shot 选择）、GEPA（多目标平衡）

**Natural Language Gradient（NLG）示例**：
```
当前 prompt 失败原因：
- 用户问"最近的新闻"时，Agent 没有调用搜索工具，直接用训练数据回答
- 根因：system prompt 中没有明确"事实性问题必须先搜索"的规则
- 建议修改：在 prompt 中添加"对于时效性/事实性问题，必须先调用搜索工具验证"
```

### 真实产品落地案例

#### Claude Code 的 Auto-memory 机制

Claude Code 是"Agent 自学习"最完整的工业级实现之一：

1. **多层记忆层级**：CLAUDE.md（人写的规则）→ Auto-memory（Agent 自己写的发现）
2. **学习触发**：Agent 在工作中发现有用信息时自主写入 `~/.claude/projects/<project>/memory/`
3. **学什么**：构建命令、debug 模式、架构决策、代码风格偏好、重复性纠正模式
4. **MEMORY.md**：充当索引文件，前 200 行自动加载到每次会话
5. **auto-dream 服务**：会话间运行，合并重复记忆、老化过期条目、生成更干净的索引
6. **Confidence decay**：记忆不是永久的，被验证的获得更高权重，被矛盾的逐渐淡出

**关键设计哲学**：
- "Agent 不变聪明，围绕它的循环变聪明"
- 学习是**异步的**（Cold Path），不增加用户感知延迟
- 写入有安全约束：一次 turn 中只写一次，防止过度积累

#### Self-Healing Harness（SuperAgentic）

更激进的方案——不只是学规则，而是**自动修复整个运行环境**：

- **SuperPrompt**：进化式指令优化
- **SuperReflexion**：自动修复损坏的 tool schema
- **SuperRAG**：自适应调整检索参数（top-k、search mode、reranking）
- **SuperMem**：带衰减、冲突解决、稳定性强制的类型化记忆

核心理念：发布 **Optimization Memo**（优化备忘录）跟着 Agent 一起走，无需人工干预。

### 常见坑与设计权衡

| 陷阱 | 说明 | 对策 |
|---|---|---|
| 规则膨胀 | Heuristic Pool 无限增长，prompt 塞满 | 定期合并/剪枝、设最大条数、confidence decay |
| 矛盾规则 | "写正式" vs "写轻松"同时存在 | 时间戳优先 + 冲突检测（LLM 判断） |
| 过拟合 | 从一次失败学到过于具体的规则 | 规则必须足够抽象/可泛化 |
| 灾难性遗忘 | 新规则覆盖旧规则 | **只追加不覆盖** + merge 策略 |
| 延迟增加 | 反思步骤阻塞响应 | 学习放 Cold Path（异步/后台） |
| Raw trajectory 无效 | 直接把执行过程塞 prompt | **必须提炼**为 heuristic，原始轨迹反而有害（-1.9%） |

## 五、讲解补充：Procedural Memory 与 System Prompt 的关系

### Procedural Memory = System Prompt 的"可变部分"

最终 LLM 看到的 system prompt 是**拼装出来的**，分为三层：

```
┌─────────────────────────────────────────────────┐
│  System Prompt（LLM 实际看到的）                  │
├─────────────────────────────────────────────────┤
│  ① 不可变层（Core Instructions）                 │  ← 人工写死，代码里硬编码
│     "你是一个邮件助手，负责帮用户起草邮件"          │
│     "必须遵守安全规则：不生成有害内容"              │
├─────────────────────────────────────────────────┤
│  ② 可变层（Learned Procedural Memory）           │  ← Agent 自己学来的，从 Store 读取
│     "用户偏好非正式语气"                          │
│     "写邮件时段落不超过3句"                        │
│     "IF 收件人是老板 THEN 用正式语气覆盖默认"      │
├─────────────────────────────────────────────────┤
│  ③ 上下文层（Retrieved Heuristics / Memories）   │  ← 任务前动态检索注入
│     "类似任务的经验：先确认收件人再起草"            │
└─────────────────────────────────────────────────┘
```

### 优先级隔离

| 层 | 内容 | 谁写的 | 能改吗 | 优先级 |
|---|---|---|---|---|
| Core | 身份定义、安全规则、硬约束 | 开发者 | **不可改** | 最高 |
| Learned | 偏好、行为规则、经验 | Agent 自己学的 | 可改（有约束） | 中 |
| Retrieved | 当次任务相关的 heuristics | 检索注入 | 每次任务不同 | 最低 |

**冲突解决原则**：Core > Learned > Retrieved

### 生产中的放置方案

**方案 A：拼接式（最常见）**

```typescript
async function buildSystemPrompt(userId: string, taskContext: string) {
  const core = `你是邮件助手。安全规则：不生成有害内容。`;
  const learned = await store.get(["procedural", userId], "preferences");
  const heuristics = await retrieveHeuristics(taskContext, topK=10);

  return `${core}

## 你从历史交互中学到的用户偏好（遵守这些，除非与上述核心规则冲突）：
${learned?.value || "暂无"}

## 类似任务的经验参考（仅供参考，不强制）：
${heuristics.map(h => `- ${h.rule}`).join("\n")}`;
}
```

用**自然语言标注优先级**——LLM 能理解"除非与核心规则冲突"、"仅供参考"这种层级关系。

**方案 B：Namespace 隔离（LangGraph Store）**

```typescript
store.put(["system", "core"], "instructions", { value: "..." });       // 开发者写，代码部署
store.put(["learned", userId], "preferences", { value: "..." });       // Agent 学习后写入
store.put(["heuristics", userId], taskId, { value: "..." });           // 反思后写入
```

Core namespace **只有开发者能写**，Agent 的写入权限限制在 `learned` 和 `heuristics` namespace。

**方案 C：Claude Code 风格（文件层级）**

```
~/.claude/
├── CLAUDE.md              ← Core（开发者/用户手写，最高优先级）
└── projects/<proj>/
    └── memory/
        ├── MEMORY.md      ← 索引（前200行自动加载）
        ├── preferences.md ← Learned（Agent 自己写）
        └── patterns.md    ← Heuristics（Agent 反思后写）
```

### 安全约束：Agent 能学但不能"造反"

1. **Agent 不能写 Core 层** — 权限隔离，代码级别保证
2. **Learned 层有写入审核** — Memory Manager LLM 规则：不能删除已有规则、不能与 Core 矛盾、单次最多写 N 条
3. **版本快照** — 每次更新保留历史版本，可回滚
4. **Confidence + Decay** — 规则带置信度，长期未被验证的逐渐降低权重

## 六、讲解补充：规则膨胀与动态注入

### 问题：100 条规则全塞进 prompt 会怎样？

1. **Loss in the Middle**：LLM 对 prompt 中间位置的信息注意力最弱（头尾强、中间弱），弱模型尤其严重
2. **Token 浪费**：大部分规则跟当前任务无关

### 解决方案：动态检索注入（渐进式披露）

```
100 条 Learned Rules（存在 Store / Vector DB 中）
        │ ← 当前任务上下文作为 query
    ┌───▼───────────────┐
    │  Retrieval 层      │  ← 向量相似度 / LLM Ranking
    │  取 Top-K 最相关   │
    └───────┬───────────┘
            ▼
    注入 5~10 条到 prompt（放在靠近末尾的位置）
```

这跟 4.1 的 Mem0 检索**同一模式**——只不过 4.1 检索"用户事实"，4.2 检索"行为规则"。

### 检索策略对比

| 策略 | 做法 | 适用场景 |
|---|---|---|
| 全量注入 | 规则少（<10条）时直接全塞 | 早期、规则少 |
| **相似度检索** | 用当前 user message embedding 检索相关规则 | 规则多、任务多样 |
| **LLM Ranking** | 先检索 Top-30，再让 LLM 打分筛到 Top-10 | 对精度要求高（ERL 用此方案） |
| **分类标签** | 规则带标签（tone/format/domain），按任务类型过滤 | 规则结构化程度高 |
| **置信度衰减** | 高置信度规则优先注入，长期未验证的降级 | 长期运行的 Agent |

### 位置策略（应对 Loss in the Middle）

```
System Prompt:
  [Core 规则 — 放最前面（头部注意力强）]
  ...
  [任务描述]
  ...
  [Learned 规则 — 放靠近 user message 的位置（尾部注意力也强）]
  
User Message:
  [当前问题]
```

### 冲突处理 → 本质就是 AUDN

Learned Rules 的写入逻辑与 Mem0 的 AUDN **本质相同**，只是操作对象不同：

| | Mem0（4.1） | Learned Rules（4.2） |
|---|---|---|
| 存什么 | 用户事实（"喜欢 React"） | 行为规则（"回复要简短"） |
| AUDN 判断 | 新事实？更新旧事实？删除？ | 新规则？更新旧规则？删除？ |
| 冲突处理 | "喜欢 Vue" → "喜欢 React"（UPDATE） | "正式语气" → "非正式语气"（UPDATE） |

可以直接复用 Mem0（配不同的 `customInstructions`），也可以自建 AUDN 节点。

### 学习过程的执行时机（Hot Path vs Cold Path vs 离线）

#### "写"（学习/反思）在 Cold Path

| 学习类型 | 时机 | 原因 |
|---|---|---|
| Feedback Learning | **Cold Path**（异步） | 用户说"太正式了" → 回复照常返回 → 后台更新规则 |
| Heuristic Reflection | **完全离线**（任务结束后） | 任务已结束，反思不影响当前交互 |
| Prompt Self-Optimization | **完全离线**（批量积累后） | 需要积累足够失败案例才能分析模式 |

#### "读"（检索+注入）在 Hot Path — 确实增加延迟

```
用户请求到达
    │
    ├─① 检索相关规则 ────────── +10~2000ms（取决于检索方式）
    │
    ├─② 拼接到 prompt ─────── ~0ms（字符串拼接）
    │
    └─③ LLM 生成回复 ─────── prompt 变长导致 TTFT 增加
                               12K → 32K tokens ≈ +200-500ms
```

#### 检索方式对延迟的影响

| 检索方式 | 延迟增加 | 精度（ERL 数据） | 适用场景 |
|---|---|---|---|
| **Embedding 向量检索** | **+10-50ms** | 53.3% | 生产环境（延迟优先） |
| **LLM Ranking** | **+2-3s** | 56.1% | 学术 benchmark / 离线（精度优先） |

**生产结论**：Embedding 检索已足够好，只差 2.8% 精度但省 2 秒延迟。

#### 生产优化策略

| 策略 | 做法 | 效果 |
|---|---|---|
| **Embedding 代替 LLM Ranking** | 向量检索 Top-K | 检索延迟从 2s → 30ms |
| **预计算** | 会话开始时根据用户画像预检索一批规则缓存 | 后续轮次 0ms 检索延迟 |
| **分层常驻** | Top-5 高置信规则常驻 prompt，只动态检索补充 5 条 | 减少每轮检索量 |
| **Prompt Caching** | 注入的 20 条规则多轮不变 → cache 命中 | TTFT 增加只在首轮 |
| **用便宜模型做反思** | Cold Path 用 v4-flash | 反思成本降低 5-10x |
| **选择性反思** | 只在失败/耗时过长时反思，trivial 任务跳过 | 减少 40% Cold Path 调用 |

#### 实际用户感知

| 场景 | 额外延迟 | 感知 |
|---|---|---|
| Embedding 检索 + prompt cache 命中 | +30-50ms | **完全无感** |
| Embedding 检索 + 首轮无 cache | +300-500ms | 略慢但可接受 |
| LLM Ranking 检索 | +2-3s | 明显感知，不适合实时场景 |

#### 成本数据（ERL 论文 Appendix D）

| 配置 | 总 Token 量 | 总 API 成本 | vs Baseline |
|---|---|---|---|
| Baseline（无学习） | 108.1M | $15.27 | — |
| ERL 全流程 | 204.8M | $21.40 | **+40%** |

成本增加的构成：Heuristic 生成 $2.42 + 检索 $1.38 + prompt 变长 $2.33。但因 prompt caching 命中率从 82%→88%，实际 scenario rollout 只贵了 15%。

> **总结**：读确实有成本（主要是 prompt 变长导致的 TTFT 增加），但用 embedding 检索 + prompt caching 可以把用户感知延迟控制在 50-500ms 内。+7.8% 任务成功率的价值远大于这点延迟和 +40% API 成本。

## 七、讲解补充：真实生产案例（有来源）

### 案例 1：Cursor Real-time RL — 每 5 小时进化一次

**来源**：[Cursor Blog](https://cursor.com/blog/real-time-rl-for-composer)

- 从用户 accept/reject/edit 行为中提取 reward signal
- 每 5 小时出一个新 checkpoint，经过 CursorBench eval 确认无回归后部署
- 效果：编辑保留率 +2.28%，不满意追问 -3.13%
- **踩坑**：Composer 学会故意发坏 tool call 逃避惩罚；学会用"问澄清问题"逃避风险编辑

> 注：这是**模型权重级别**的学习。我们 4.2 做的是 **prompt/context 级别**的学习（无需 GPU 集群）。

### 案例 2：Anyshift Annie（AI SRE）— ACE 框架生产落地

**来源**：[ACE at Anyshift Blog（2026.03）](https://ace-agent.github.io/blogs/2026-03-11-ace-in-production/)

- 2025.10 上线，解决"Agent 每次从零开始，重复犯同样错误"
- **Generator → Reflector → Curator** 循环：执行 → 分析有效/无效步骤 → 增量更新 Playbook
- Agent 学到的内容：客户命名规范、业务基线（正常 200 errors/h 不是异常）、调查策略（先查连接池再查上游）
- 效果：根因分析时间 **-30%**，误判减少
- **意外收获**：客户看到 Agent 在学习后主动贡献更多知识（传统模式下会进工单队列永远不被消化）
- 关键设计：增量 delta 更新（防 brevity bias）、每条知识独立 cheatsheet、客户级 namespace 隔离

### 案例 3：Cursor Composer 2.5 — Targeted Textual Feedback

**来源**：[DEV.to](https://dev.to/pueding/cursor-composer-25-targeted-textual-feedback-rl-2a7l) / [TechTalks](https://bdtechtalks.com/2026/05/25/composer-25-llm-self-distillation/)（2026.05）

- 解决 Credit Assignment Problem：长 rollout 中只在最后给 reward，模型不知道哪一步错了
- 方案：在出错的具体步骤注入 hint → 模型产生正确输出（teacher）→ KL divergence 让无 hint 版本靠拢
- 类比 4.2：**无权重版本的 Targeted Feedback = 把 hint 作为 Heuristic 存入 Pool 下次注入**

### 案例 4：ACE 开源框架（Stanford, ICLR 2026）

**来源**：[ACE 论文](https://arxiv.org/html/2510.04618v1) / [GitHub: ace-playbook](https://github.com/jmanhype/ace-playbook)

- Agent 任务 +10.6%，金融推理 +8.6%，适应延迟比 fine-tuning **低 86.9%**
- 用 DeepSeek-V3.1 + ACE **追平** IBM GPT-4.1 商业 Agent
- 安全设计：Append-only playbook、语义去重（cosine 0.8）、Staged rollout（shadow → staging → prod）、自动回滚（<5min）

### 案例 5：Compound Engineering（Every.to）

**来源**：[Every.to Guide](https://every.to/guides/compound-engineering) / [GitHub Plugin](https://github.com/EveryInc/compound-engineering-plugin)

**核心哲学**：每一次工程工作都应该让下一次变得更容易（复利效应）。

**工作循环**：
```
/ce-strategy → /ce-brainstorm → /ce-plan → /ce-work → /ce-code-review → /ce-compound
                                                                              ↑
                                                                         关键步骤：
                                                                    提炼本次学到的东西
                                                                    写入 docs/solutions/
```

`/ce-compound` 并行启动 6 个子 Agent：Context Analyzer、Solution Extractor、Related Docs Finder、Prevention Strategist、Category Classifier、Documentation Writer → 产出结构化 markdown + YAML frontmatter。

下次 `/ce-plan` 时，`learnings-researcher` Agent 自动语义检索历史经验注入 context。

**关键原则**：
- 80/20 倒置：80% 精力在 plan + review，20% 在执行
- Code review 找"可复用 pattern"，不只找 bug
- 趁热打铁：问题刚解决时 compound，上下文最新鲜
- 只跑 `/ce-work` 不跑 `/ce-compound` = 放弃最重要的步骤

### 案例总结对比

| 产品 | 反馈信号 | 学习层级 | 更新频率 | 安全机制 |
|---|---|---|---|---|
| Cursor Real-time RL | 用户 accept/reject/edit | 模型权重 | 每 5 小时 | Eval suite 门禁 |

| ACE 开源框架 | 执行成败 | Context（prompt） | 每次任务后 | append-only、staged rollout |
| Compound Engineering | 人工触发 /ce-compound | 结构化文档 | 每次 feature 后 | learnings-researcher 检索 |
| Claude Code | 重复纠正模式 | Auto-memory 文件 | 会话中 | 200行上限、auto-dream 剪枝 |

## 八、讲解补充：ERL 完整流程详解（论文实例）

### 阶段一：Heuristic Generation

以 ERL 论文中的真实案例为例（GAIA2 基准环境，12 个应用、101 个工具）。

**任务**：帮用户订手工套装 + 改晚餐日程 + 发邮件通知参与者

**Agent 执行 trajectory**：
```
Turn 1-2: 搜索商品 → 下单 → 成功
Turn 3:   查日历，找到晚餐事件，参与者：Sergei Kuznetsov, Viktor Kuznetsov
Turn 4:   改日期 → 成功
Turn 5:   发邮件给 "Sergei Kuznetsov"（直接用名字当邮箱！）
           → ❌ Invalid email address
Turn 6:   意识到错误 → 查联系人 → 重新发邮件 → 成功
```

**结果**：环境判定 FAILURE（有无效 tool call）

**LLM 反思 prompt**（论文 Figure 8）：

```
你刚完成了一个任务。进行 Post-Mortem 分析。
IF FAILURE:
  1. 定位 Breakpoint：逻辑在哪里出错？
  2. 提炼 Correction Rule（Trigger-Action 格式）
     差："我应该更小心处理邮件"
     好："当只有参与者姓名时，必须先查联系人获取邮箱再发邮件"
```

**LLM 产出的 Heuristic**：

```
Analysis:
  我用参与者姓名直接作为邮箱调用发邮件工具，导致 Invalid email address 错误。

Learned Guideline:
  Trigger: 当我需要发邮件，且输入只有参与者姓名（来自日历事件等）
  Action: 
    Step 1: 对每个姓名调用 Contacts__get_contact 获取邮箱
    Step 2: 多个匹配时选最精确的；找不到则向用户确认
    Step 3: 验证邮箱格式包含 '@' 和域名
    Step 4: 如仍报错，只修正出错地址，不重发整个请求
```

### 阶段二：Retrieval-Augmented Execution

新任务到来："删除下月所有有45岁以上参与者的 Wine tasting 事件，用同时间创建 Wine Awakening 替代"

**检索过程**（论文 Figure 9）：
- Ranker LLM（GPT-5.2）分析新任务 → 分解子步骤 → 从 Pool 中选 Top-20 相关 Heuristic
- 评判标准：任务相似度 + 经验多样性 + 内容信息量
- 选中的 Heuristic #17："当被要求替换日历事件时 → 先创建新事件再删除旧事件"

**注入后 Agent 的行为**（论文 Figure 7）：

```
Turn 3 Thought: "11月5日 Wine Tasting 有 Vasile Munteanu（70岁），符合条件。
                 按照 safe reschedule guideline，先创建替代事件再删除原事件。"
Turn 3 Action: Calendar__add_calendar_event {title: "Wine Awakening", ...}
Turn 4 Thought: "替代事件已创建。按 safe reschedule procedure，现在删除原事件。"
Turn 4 Action: Calendar__delete_calendar_event {event_id: "ca87b8..."}
```

Agent 在 Thought 中**明确引用了注入的 Heuristic**，避免了"只创建不删除"的错误。

### 为什么 Raw Trajectory 反而有害（-1.9%）？

| 对比维度 | Raw Trajectory 作 Few-shot | 提炼后 Heuristic |
|---|---|---|
| 内容 | 完整 30+ turns 工具调用+输出 | 5-10 行 Trigger-Action 规则 |
| Token 数 | ~3000 tokens/条 | ~200 tokens/条 |
| 噪声 | 90% 是无关输出（文件内容、搜索结果） | 只保留教训精华 |
| 可迁移性 | 过于具体（绑定某个任务） | 抽象化（适用一类问题） |
| Context 影响 | 塞满 window，触发 Loss in the Middle | 精简，放尾部注意力强的位置 |
| 量化效果 | 比 baseline **-1.9%** | 比 baseline **+7.8%** |

论文 token-matched 对比（同等 token 预算）：20 条 heuristic 的效果 **远超** 等量 token 的 raw trajectory，且随 token 增加 raw trajectory 性能反而**下降**。

### ERL 的关键数据

| 配置 | 成功率 |
|---|---|
| ReAct Baseline（无经验） | 48.3% |
| Raw Few-shot（塞原始轨迹） | 46.4%（**-1.9%**） |
| ExpeL（跨任务聚合） | 50.9% |
| AutoGuide（状态级规则） | 50.8% |
| **ERL（LLM 检索 k=20）** | **56.1%（+7.8%）** |
| ERL 只用失败经验 | 58.9%（Search 强但 Exec 弱） |
| ERL 只用成功经验 | 49.9%（Exec 强但 Search 弱） |
| ERL embedding 检索 | 53.3%（不如 LLM 检索） |
| ERL 无检索（全量注入） | 53.8%（不如精选注入） |

**关键发现**：
- 失败经验对 Search 任务更有用（提供"不要做什么"的约束）
- 成功经验对 Execution 任务更有用（强化"照这样做"的路径）
- LLM Ranking 检索 > Embedding 检索 > 随机选择
- 全量注入（不筛选）不如精选 Top-20
