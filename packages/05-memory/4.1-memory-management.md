## 一、行业调研报告（Industry Research）

### 1. 核心收敛：四层记忆分类法（业界 2026 已成共识）

> 上次讲解只覆盖了三类（Working / Episodic / Semantic），漏了 **Procedural（程序性）**。
> Procedural 是 Cursor / Claude Code 这类产品最核心的一类，必须补上。

| 类型 | 内容 | 类比（人脑） | 实现 | 检索 | 衰减 |
|---|---|---|---|---|---|
| **Working** | 当下推理输入 | 短期意识 | Context window / messages 数组 | 永远在场 | token 上限硬截断 |
| **Episodic（情景）** | 发生过什么事（带时间） | 海马体 | 事件日志 + 时间索引 + 向量索引 | 相似度 + 近因 | 时间衰减 |
| **Semantic（语义）** | 稳定的事实/偏好 | 大脑皮层 | 知识图谱 / 结构化 KV / 向量库 | 相似度 + 关系 | 手动失效（被新事实顶替） |
| **Procedural（程序性）** | 怎么做事（工作流、规则） | 小脑 | System prompt / 配置文件 / 工具定义 | 永远在场 | 版本控制 |

### 2. 主流产品的真实映射

| 产品 | Working | Episodic | Semantic | Procedural |
|---|---|---|---|---|
| **Claude Code** | context window | 对话历史（自有持久化机制） | MEMORY.md（auto-memory） | CLAUDE.md + .claude/rules/ |
| **Cursor** | context window | session 缓存 | 用户偏好（向量索引） | .cursorrules + AGENTS.md |
| **LangGraph 生态** | State.messages | Checkpointer | Store API | 写在 SystemMessage 里（手工） |
| **Mem0** | -（不管） | 事件 store | 抽取后的 fact store | -（不管） |
| **Zep** | -（不管） | 时序图谱节点 | 带 validity 的图谱节点 | -（不管） |
| **Letta（MemGPT）** | Core Memory | Recall Memory | Archival Memory | 工具定义 |

### 3. 生产宪法：Hot / Cold Path 分离

**这是 Anthropic、Microsoft Azure、Oracle、Mem0、Zep、Letta 都遵守的设计原则，没有例外。**

```
┌──────────────────────────────────────────────────────────────┐
│ 🔥 HOT PATH（用户能感觉到延迟的地方）                          │
│                                                              │
│   用户问题 → 检索相关记忆 → 拼装 context → LLM → 响应         │
│                                                              │
│   SLA：< 200ms 检索延迟                                       │
│   原则：永远不阻塞写入                                        │
└──────────────────────────────────────────────────────────────┘
                            ↓ fire-and-forget 事件
┌──────────────────────────────────────────────────────────────┐
│ 🧊 COLD PATH（用户感觉不到的后台）                             │
│                                                              │
│   事件入队 (Redis Streams / Kafka)                            │
│      ↓                                                       │
│   PII 脱敏（合规要求）                                         │
│      ↓                                                       │
│   LLM 抽取关键事实（Episodic → Semantic）                     │
│      ↓                                                       │
│   去重 / 矛盾消解（AUDN gate）                                │
│      ↓                                                       │
│   写入持久层（Postgres + pgvector / 知识图谱）                │
│                                                              │
│   SLA：可以慢，但要可观测、可重试                              │
└──────────────────────────────────────────────────────────────┘
```

**实测数据**：同步写入会让 p95 延迟增加 **300-500ms**（嵌入计算 + LLM 抽取 + 数据库写）。

> "Hot/Cold 分离不是性能优化，是**正确性属性**。同步写入污染延迟 SLA，并引入 race condition。"
> —— Milam & Gulli, 《Context Engineering: Sessions, Memory》（业界引用最广的一篇）

### 4. 写入策略：Curation Gate（AUDN 模式）

**关键**：**不能 append-only**。Mem0 论文（arXiv:2504.19413）实测：append-only 系统跑 3 个月后，**40-60% 的事实是过期或矛盾的**；加 curation gate 可让矛盾率下降 **80%+**。

每次写入前，让小 LLM 做四叉决策：

| 决策 | 触发条件 | 操作 |
|---|---|---|
| **A**dd | 没有相关已有事实 | 新建节点 |
| **U**pdate | 演进现有事实（"完成 50%" → "完成 80%"） | 旧版归档（带时间戳），新值生效 |
| **D**elete/Supersede | 直接矛盾（"住伦敦" → "搬巴黎"） | 旧的标 superseded，新的成为当前真相 |
| **N**o-op | 重复信息 | 跳过，旧节点 importance 微涨 |

LangGraph 的 `Store` **不内置** curation——这是应用层逻辑要自己实现。

### 5. 检索策略：Hybrid Retrieval

**纯向量是新手陷阱**。生产环境一致采用 **BM25 + Vector + RRF**（Reciprocal Rank Fusion）：

```
查询 → ┬─ BM25（关键词精确匹配）─┐
       └─ Vector（语义相似）   ─┴→ RRF 融合 → top-k
```

**实测**：比纯向量好 **15-30%**（recall）。原因：纯向量会把"ORD-123"和"ORD-456"编码成同一语义簇区分不了，BM25 通过字符串精确匹配弥补这个空隙。

#### 为什么是 BM25？

关键词检索有多种方案，BM25 是 30 年工程实践验证的工业标准：

| 方案 | 问题 |
|---|---|
| `LIKE '%keyword%'` | 不考虑词频和稀有度，排序质量差 |
| TF-IDF | BM25 的前身，有两个已知缺陷 |
| **BM25** | 修复了 TF-IDF 的缺陷，Elasticsearch 默认算法 |

**TF-IDF 的两个缺陷及 BM25 的修复**：

缺陷 1 — 词频无上限：TF-IDF 里一个词出现 100 次比出现 1 次好 100 倍，但实际相关性差距没那么大。BM25 加 k1 参数（通常 1.5）让词频贡献趋于饱和。

缺陷 2 — 长文档天然优势：长文档更可能包含关键词但不一定更相关。BM25 加 b 参数（通常 0.75）做文档长度归一化。

#### 为什么是 RRF？

融合多路检索的核心难题是**分数尺度不统一**——BM25 分可能是 2.9，余弦相似度是 0.7，直接相加没有意义：

| 融合方案 | 问题 |
|---|---|
| 分数直接相加 | 尺度不同，无意义 |
| 归一化后相加 | 需要全局最大/最小分，对 outlier 敏感，流式场景难实现 |
| 学习排序（LTR） | 需要大量标注数据，成本高 |
| **RRF** | 只用排名不用分数，尺度无关，无需训练，效果稳定 |

RRF 公式：`score(d) = Σ 1/(k + rank_i(d))`，k=60 来自论文实验，在大量场景下稳定有效。核心洞察：**排名是通用语言**，不管原始分数是什么单位，第 1 名就是第 1 名。

#### 生产实现方案

```
方案 A：Elasticsearch（生产最常见）
  BM25 内置，向量检索 8.x+ 支持，RRF 8.14+ 内置
  → 一个系统全搞定

方案 B：Postgres + pgvector + tsvector（不想引入 ES 时）
  pgvector → 向量检索
  tsvector → 全文检索（BM25 近似实现）
  RRF → 应用层手写

方案 C：专用向量库 + BM25 库（向量规模极大时）
  Pinecone / Qdrant + Tantivy / BM25s
  RRF → 应用层手写
```

**Mem0 / Zep 做了什么**：把上述方案封装成一行 `client.search(query)`，你不用关心两路召回和 RRF 融合的细节。

#### RRF 的已知局限

当 BM25 对某条 query 完全无效（所有文档关键词分为 0）时，BM25 路不是安静退出，而是以随机噪声形式干扰向量结果。生产解法：
- **加权 RRF**：给向量路更高权重
- **条件 fallback**：BM25 最高分为 0 时直接用纯向量结果

可选叠加：
- **Graph traversal**：处理多跳关系（"Alice 和 Bob 合作过哪些项目？"）
- **Cross-encoder rerank**：粗排后用精排模型二次排序，提升 precision
- **Temporal weighting**：近期记忆加权（Zep 的 validity window 是这个思路的极致版）

### 6. 主流框架横评（2026-04 实测）

#### LangGraph（我们正在学的）

- **短期**：`Checkpointer` —— `MemorySaver`（开发）/ `SqliteSaver`（单机）/ `PostgresSaver`（生产）
- **长期**：`Store` API —— `InMemoryStore` / `PostgresStore`（生产，自带 pgvector 语义检索）
- **关键设计**：`thread_id` 隔离短期 / `user_id` 跨 thread 共享长期
- **生产建议**：直接用 `PostgresSaver`（JS/TS SDK 天然异步），**跳过 SqliteSaver**（写锁是单库级，并发会爆）

#### Pydantic AI

- **没有内置长期记忆**（作者明确表态："不想 anoint 任何 DB"）
- **短期**：`message_history` 参数 + `ModelMessagesTypeAdapter` 序列化到 JSON/SQLite
- **核心特色**：`history_processors` —— 一组可组合的中间件，每次发给 LLM 前修改消息历史
- **典型 processor**：keep-only-recent / summarize-old / filter-PII
- **长期**：必须外接（社区方案：Hindsight、agentmem 等）

#### Mem0（最易集成的专用 memory 层）

- **架构**：被动抽取 + 语义检索 + 可选图存储
- **性能**：1.44s p95 / 91% token 节省 / LOCOMO 66.9%
- **集成**：1 行代码即可；**21 个框架开箱即用**
- **缺点**：图记忆只在 Pro 版（$249/月，13× 价格阶跃）

#### Zep / Graphiti

- **杀手锏**：**双时态知识图谱**——每个事实带 validity window（"2024 年用户在伦敦，2025 年起在巴黎"）
- **性能**：4s avg latency（要按这个量级设计架构）/ LongMemEval 63.8%
- **适合**：CRM、医疗、金融等需要"什么时候是真的"的场景

#### Letta（MemGPT）

- **不是 memory 层，是 agent runtime**——这点要分清
- 三层：Core（context 内常驻）/ Recall（缓存）/ Archival（冷存）
- LLM 自己通过 `archival_memory_search` 等工具操作记忆
- **锁定严重**：换走等于重写整个 agent

#### Coding Agents（Cursor / Claude Code）

- **核心：Procedural Memory 标准化**
- **AGENTS.md**：跨工具开放标准（Cursor、Codex、GitHub Copilot 都读）
- **CLAUDE.md**：Anthropic 专有，支持层级加载（user → project → local）、`@imports`、path-scoped rules
- **MEMORY.md**：Claude Code 的 auto-memory，自己学到的写自己（200 行 / 25KB 上限）
- **生产做法**：`ln -s AGENTS.md CLAUDE.md`，单一来源，多工具共享

### 第 0 站：起点

你已经会写 ReAct Agent 了。最初的 Memory 就是一行代码：

```typescript
const messages = [];
messages.push(new HumanMessage("我叫 Alice"));
const resp = await llm.invoke(messages);
messages.push(resp);
// 下一轮，Alice 说"我刚才叫什么名字？"
messages.push(new HumanMessage("我刚才叫什么？"));
const resp2 = await llm.invoke(messages); // 它能答出 Alice
```

**这就是 Memory 的全部？** 几乎是的——只要对话不长、不换会话、不犯错。

下面我们逐个增加约束，看会出什么问题。

---

### 第 1 站：对话变长了

#### 真实场景

你在做客服 Agent。一个用户问售后问题，前后聊了 200 轮。

模型 context 是 128k tokens，对话累积到 100k+ 时：
- 响应变慢
- 模型开始忘记早期信息（"lost in the middle" 现象）
- 直接报错 `context_length_exceeded`

#### 朴素解法 1：滑动窗口

只保留最近 N 条消息：

```typescript
if (messages.length > 50) {
  messages = messages.slice(-50);
}
```

**够用吗**？分场景：
- ✅ 单次咨询（问完就走） → 够
- ❌ 长尾客服（断断续续聊一周）→ 早期信息（订单号、用户身份）丢了

#### 朴素解法 2：LLM 摘要替换

把前 40 条消息让 LLM 压成一段摘要，挂到 system prompt：

```typescript
if (messages.length > 50) {
  const summary = await llm.invoke([
    new SystemMessage("把以下对话压缩成一段不超过 200 字的事实摘要："),
    ...messages.slice(0, 40),
  ]);
  messages = [
    new SystemMessage(`# 早期对话摘要\n${summary.content}`),
    ...messages.slice(40),
  ];
}
```

**够用吗**？比滑动窗口好多了，但多了一次 LLM 调用（成本/延迟）。

#### 第一个概念诞生：**Working Memory（工作记忆）**

我们刚才折腾的，本质上都是在管理"**这一次发给 LLM 的 messages 数组**"。这一类东西业界给了个名字：**Working Memory**——可以理解为人脑里的"短期意识"，是当下推理用的工作台。

> 注意：到现在为止，我们一行 LangGraph 都没用。Working Memory 是任何 LLM 应用都要解决的第一个问题。

---

### 第 2 站：换会话就失忆

#### 真实场景

用户今天告诉 Cursor "我用 pnpm，不要用 npm"。
明天打开新对话，Cursor 又给了 `npm install`。

#### 为什么？

我们刚才的 messages 数组**只活在内存里**，进程一停就没了。即使存到磁盘，**新会话也不会去读旧会话的 messages**——它压根不知道你以前说过什么。

#### 朴素解法：把对话历史持久化

每次对话开始前，从数据库把上次的 messages 加载回来。这就是 LangGraph 的 **Checkpointer** 在做的事：

```typescript
const graph = builder.compile({ checkpointer: new MemorySaver() });
graph.invoke(input, { configurable: { thread_id: "alice-1" } });
// 关掉重开，只要 thread_id 一样，messages 自动恢复
```

#### 第二个概念诞生：**Short-term Memory（短期记忆）**

把"会话内的 messages"持久化下来，让你**关掉重开**还能继续——这就是 Short-term Memory。生产里 LangGraph 推荐 `PostgresSaver`，本质就是把 messages 写进 Postgres 而已。

#### 但马上又遇到新问题

Cursor 不只是"延续旧对话"。它需要在**完全新的对话**里也记得你用 pnpm。

如果你用 `thread_id="alice-1"` 存今天的对话，明天用 `thread_id="alice-2"` 开新对话，**Checkpointer 不会跨 thread 共享**——这是它的设计：每个 thread 是独立的状态机。

> 这是 Short-term Memory 的天花板：作用域是单个 thread。

要让"我用 pnpm"跨所有对话生效，得换一种存法。

---

### 第 3 站：从"对话历史"到"知识"

#### 真实需求

我们想要的不是"把昨天的对话调出来"，而是"昨天聊出来的**关键事实**今天还能用"。

具体说，从昨天的 200 轮对话里，真正值得带到今天的可能只有一句：
> "用户偏好 pnpm。"

剩下 199 轮都是过程，不需要带。

#### 朴素解法：手动提炼

会话结束时，让 LLM 看完整对话，提炼成几条事实，存到一个**跨 thread 的 KV 库**里：

```typescript
const facts = await llm.invoke([
  new SystemMessage("从以下对话里提炼用户偏好，每条一行，简洁。"),
  ...messages,
]);
db.put(`user:${userId}:facts`, facts);
```

下次开新对话，先读这个 KV，把事实塞 system prompt：

```typescript
const facts = db.get(`user:${userId}:facts`);
const systemPrompt = `用户已知偏好：\n${facts}`;
```

#### 第三个概念诞生：**Long-term Memory（长期记忆）**

跨 thread、跨会话、跨"任何 thread_id"都活着的记忆。

LangGraph 把这叫 **Store API**（与 Checkpointer 并列），生产里推荐 `PostgresStore`：

```typescript
store.put(["user", userId], "pref_pkg_manager", { value: "pnpm" });
const pref = await store.get(["user", userId], "pref_pkg_manager");
```

> 重要：**Checkpointer 和 Store 是两个东西**。
> Checkpointer 存"thread 内的状态机"；Store 存"thread 之外的知识"。
> 你不能用 Checkpointer 当 Long-term，因为它跟着 `thread_id` 走。

---

### 第 4 站：长期记忆该存什么、怎么存？

#### 第一个分歧：两种"知识"长得不一样

我们再仔细看两个例子：

**例子 A**：
> "用户在 2025-04-15 14:32 抱怨订单 #ORD-123 物流延迟，最后接受了 30% 折扣。"

**例子 B**：
> "用户偏好 TypeScript。"

它们都是"事实"，但很不一样：
- A 有**时间戳**，是"发生过的具体事件"
- B 是**稳定的状态**，没有特定时间点

更关键的是，**它们的查询方式完全不同**：
- A：用户问"上次那个订单怎么处理的？"——按近因 + 关键词查
- B：每次推荐技术方案前都需要——直接读用户偏好字段

如果都塞同一个表，要么 A 把 B 淹没（事件太多），要么 B 拖慢 A 的检索（每次都要扫一遍）。

#### 业界的命名

工业界把这两类记忆分别叫：

- **Episodic Memory（情景记忆）**：发生过什么事，带时间戳，存事件流
- **Semantic Memory（语义记忆）**：稳定的事实/偏好，存结构化字段或向量

> 这个分类不是凭空发明的，**是认知科学里早就有的概念**（人脑的海马体 vs 大脑皮层）。AI 工程师只是借用了这个分类，因为它真的对应了两种检索/失效模式。

---

### 第 5 站：长期记忆怎么找回？

现在你存了 1000 条事实在 Long-term Store 里。新对话开始时，**全部塞进 prompt 显然不行**——又回到 context 爆炸。

只能选**和当前对话相关**的几条塞进去。怎么选？

#### 朴素解法 1：精确 KV

```typescript
store.get(["user", "alice"], "pref_pkg_manager"); // → "pnpm"
```

**够用吗**？只在你**预先知道要查什么 key** 时管用。
真实场景：用户问"上次那个订单"，你不知道订单号，只能模糊匹配。

#### 朴素解法 2：语义检索（向量）

精确 KV 的根本问题：**你必须预先知道要查什么**。但用户发来的是一句自然语言，你没法猜 key。

语义检索的思路：用 **Embedding 模型**把每条事实转成一组数字（向量），语义越近的文本向量越接近。查询时把用户的话也转成向量，按余弦相似度排序，找最相关的 top-k。

```typescript
const memories = await store.search(["user", "alice"], {
  query: "帮我推荐一个前端框架",  // 自然语言，不需要知道 key
  limit: 3,
});
// → 自动找到 "用户对 React 和 Vue 都有经验"（语义相关）
// → 自动找到 "用户偏好 TypeScript"（有关联）
// → 不会返回 "用户住在上海"（语义无关）
```

**这就是语义检索的核心价值：用户用自然语言随便问，系统能从一堆记忆里自动找到相关的。** 不需要预知 key，不需要设计 filter 字段，只要"意思相近"就能命中。

**绝大多数场景语义检索够用了**。但它有两个已知的失败模式：

##### 失败案例 1：精确实体名

用户问 "我的订单 ORD-123 现在什么情况？"

向量检索看到的是"语义相似"。它会返回：
- ✅ "用户提到订单状态" （相关，但不是这个订单）
- ✅ "物流相关的对话" （相关，但订单号不同）
- ❌ 漏掉真正提到 "ORD-123" 的那条

为什么？嵌入模型把 "ORD-123"、"ORD-456"、"ORD-789" 编码成相似的向量（都是"订单号"这个语义簇），区分度反而不如关键词匹配。

##### 失败案例 2：技术术语

用户问 "PostgreSQL 配置怎么改"

向量检索可能返回：
- ✅ "数据库设置教程"（相似，但不准确）
- ❌ 漏掉真正写了 "PostgreSQL" 的那条（排序靠后）

#### 第三种思路：把两个一起用

那能不能把"关键词精确匹配"和"语义相似"**同时**做，再合并？

可以。这种叫 **Hybrid Retrieval**：

```
查询 ──┬─ 关键词检索（BM25 算法）──┐
       └─ 语义检索（Vector）       ──┴─→ 用 RRF 算法融合 ─→ top-k
```

**RRF（Reciprocal Rank Fusion）** 是个朴素到不能再朴素的算法：每条结果在两个排名里都加分，谁两边都排前面就胜出。不要被名字吓到。

**实测效果**：业界一致测出 Hybrid 比纯向量好 **15-30%**（recall 维度）。

> 现在你应该懂为什么生产环境一致用 Hybrid 而不是纯向量了——不是因为它"高级"，是因为纯向量在两个具体场景会 fail。

#### LangGraph 的现状

`PostgresStore` 配合 pgvector 支持向量检索，Postgres 本身也有全文检索能力（`tsvector`），但 LangGraph Store API 层面的 `search()` 只暴露了向量检索（`query` 参数）和 filter 精确匹配，**未内置 BM25 + 向量的 Hybrid Retrieval**。真正的 Hybrid 需要自己在应用层组合两路召回 + RRF 融合。`InMemoryStore` 配置 `IndexConfig` 后同样支持向量检索（够开发用）。

### 第 6 站：长期记忆跑久了会出怪事

#### 真实事故（业界叫 Context Schizophrenia）

用户 4 月 1 日说："我住在伦敦。"
4 月 15 日说："我搬到巴黎了。"

如果你的写入策略是**"看到事实就追加"**（append-only），现在 Long-term Store 里有两条：
- "用户住伦敦"
- "用户住巴黎"

5 月 1 日用户问："离我最近的咖啡店推荐？"
向量检索返回**两条都匹配**，因为它们语义都是"用户位置"。

Agent 该信哪条？
- 选错了：用户在巴黎却推荐伦敦的店，体验崩
- 全塞 prompt 让 LLM 自己选：LLM 没有时间感，可能选错；而且这种"两面三刀"的 prompt 让 LLM 更容易胡说

**Mem0 团队的论文（arXiv:2504.19413）实测**：append-only 系统跑 3 个月，**40-60% 的事实是过期或矛盾的**。

#### 朴素解法：写入前先比对

每次要写新事实时，先查"最相似的已有事实"，让 LLM 判断这是新增还是冲突：

```typescript
async function smartWrite(newFact: string) {
  const similar = await store.search(namespace, { query: newFact, limit: 3 });
  const decision = await llm.invoke([
    new SystemMessage(`已有事实：${similar.map(s => s.value.fact).join("\n")}
新事实：${newFact}
请输出：ADD（新信息）/ UPDATE（演进）/ SUPERSEDE（矛盾）/ NOOP（重复）`),
  ]);
  switch (decision) {
    case "ADD": store.put(...);
    case "UPDATE": store.update(...);
    case "SUPERSEDE": markOldSuperseded(); store.put(...);
    case "NOOP": /* skip */;
  }
}
```

#### 业界的命名：**AUDN Gate**

把这四种决策标准化：**A**dd / **U**pdate / **D**elete-Supersede / **N**oop。Mem0 论文证明：加了这道 gate，矛盾率下降 **80%+**。

> 看到了吗？这不是什么"高深的设计模式"，**就是写入前查一下、用 LLM 仲裁一下**。但不做和做的差距是 80% 矛盾率。

### 第 7 站：写入太慢，把响应拖垮了

承接上一站。我们刚加了 AUDN Gate，每次写入要做：
1. 查相似事实（嵌入计算 + 向量搜索） ~50ms
2. LLM 仲裁决策 ~200-500ms
3. 写入数据库 ~30ms

合计**约 300-500ms**，每条事实写入都要这么久。

#### 朴素方式：在响应路径里同步写

```typescript
async function chat(userMsg: string) {
  const memories = await store.search(...);     // 30ms
  const response = await llm.invoke(...);       // 1500ms
  await smartWrite(extractFacts(response));     // 300-500ms ← 新加的
  return response;
}
```

p95 响应时间从 1.5s 涨到 2s。在并发场景下还可能踩死锁（两个请求同时改同一个事实）。

#### 解法：把"写"挪到响应之后

响应先返回给用户，写入丢给后台异步处理：

```typescript
async function chat(userMsg: string) {
  const memories = await store.search(...);
  const response = await llm.invoke(...);
  queue.publish({ event: "turn", userMsg, response }); // 微秒级
  return response; // ← 立即返回
}

// 后台 worker（独立进程/协程）
async function memoryWorker() {
  while (const event = await queue.pop()) {
    const facts = await llm.extract(event);
    await smartWrite(facts);
  }
}
```

#### 业界的命名：**Hot Path / Cold Path 分离**

- **Hot Path**：用户能感觉到延迟的路径，只做"读 + 推理 + 响应"
- **Cold Path**：后台异步处理"提炼 + 写入 + 整理"

> 看到了吗？这也不是什么"宪法级设计原则"，**就是把慢的活儿挪到后台**。但很多新手代码就是直接 await 写入，p95 就崩了。

#### 为什么我之前说它"是正确性属性，不只是性能"

因为：
- 同步写引入 race condition（并发请求改同一事实）
- 写失败会污染响应（用户看到 500 错误）
- 后台重试能力是 GDPR 删除请求的合规要求

但这些是**进阶视角**。本站只要先记住"慢的活儿挪后台"就够。

### 第 8 站：还有一类记忆 Long-term 处理不了

#### 真实场景

你告诉 Claude Code："我们项目用 pnpm，写代码不要加注释。"

第二天新对话，理论上 Long-term Memory 应该能记得。但：
- 向量检索可能漏召回（"项目规则"和当前问题语义不一定相关）
- 召回了也可能被 LLM 忽视（埋在一堆事实里）
- **每次出错都是不可接受的**（这是规则不是偏好）

#### 关键洞察

这类信息的特点：
- **永远适用**（不是"上次的订单"，是"以后写代码都要遵守"）
- **不允许漏检**（漏了就犯错）
- **数量有限**（一个项目几十条规则就够了）

那为什么要"检索"？直接**永远塞进 system prompt** 不就好了？

#### 业界的做法

**Cursor**：项目根目录放 `.cursorrules` / `AGENTS.md`，每次对话都自动加载到 system prompt。

**Claude Code**：`CLAUDE.md` + `.claude/rules/*.md`，支持层级（user/project/local）、`@imports`、按文件路径条件加载。

**它们的本质**：把"必须永远遵守的规则"**固化为 system prompt**，永远在场，永不漏检。

#### 第四个概念诞生：**Procedural Memory（程序性记忆）**

"怎么做事"的记忆，类比人的**肌肉记忆**（小脑），不需要"想"，自动执行。

实现就是 Markdown 文件 + 加载到 system prompt。简单粗暴，但有效。

> 这是 Coding Agent 领域的护城河之一——能写好 `CLAUDE.md` 的团队，Agent 表现明显高一截。

## 五、消化记录（暂停 3 Q&A）

### Q1：Working Memory

**学生理解**：就是发送给 LLM 的 messages 数组，由长短期记忆、用户消息等构成。

**老师补充**：准确。Working Memory 是其他三类记忆的**汇聚口**，不是独立的一"种"记忆：

```
Working Memory（发给 LLM 的 messages）
├── System Prompt（含 Procedural Memory）
├── 注入的 Long-term 事实（Semantic/Episodic 检索结果）
├── Short-term 对话历史（本 thread 近期消息）
└── 当前用户输入
```

生产环境的核心挑战是**预算分配**——128k token 的窗口里各部分分多少。

### Q2：Hot/Cold 分离

**学生理解**：提升鲁棒性及性能。

**老师补充**：拆成三层理解更精确：

| 层 | 具体问题 |
|---|---|
| **性能** | 用户不等写入完成 → p95 降低 |
| **正确性** | 写入走队列串行化 → 避免 race condition（并发写同一字段导致数据错） |
| **可靠性** | 写入失败可重试 → 不丢数据、不影响已返回的响应 |

并发场景举例：用户连续发两条消息改住址，同步写入可能后发先至导致最终数据是旧的。

### Q3：AUDN 实战

**学生判断**：Day 1 = Add ✅，Day 5/30/60 不确定。

**老师补充完整时间线**：

| Day | 用户说的 | AUDN | 关键原因 |
|---|---|---|---|
| 1 | "我住在伦敦" | **Add** | 无已有事实 |
| 5 | "我下个月要搬到巴黎" | **Add** | "计划"≠"现状"，两条并存 |
| 30 | "我已经搬到巴黎了" | **Supersede** | "住伦敦" 被标记 superseded |
| 60 | "其实我又搬回伦敦了" | **Supersede** | "住巴黎" 被标记 superseded |

**关键认知**：AUDN 的真正难点在 Day 5 这种"意图 vs 现状"灰色地带，这是 curation gate 里用 LLM 做仲裁的核心价值——规则难穷举，LLM 能理解语义。

**共识**：订单号 `ORD-123` 这种精确实体名，向量检索无法区分 ORD-123/456/789（都编码成"订单"语义簇），BM25 能精确命中字符串。

---

### 追问 Q3-1：AUDN 有没有行业规则推荐？

**核心原则**：AUDN 的策略要根据记忆类型来定，不是一刀切。

| 记忆类型 | 写入策略 | 原因 |
|---|---|---|
| **Episodic** | 永远 Add（append-only） | 事件是"发生过的事"，不存在矛盾 |
| **Semantic** | 完整 AUDN，LLM 仲裁 | 事实会变化，矛盾需要消解 |
| **Procedural** | 版本控制，人工审核 | 规则变更影响面大，不能让 LLM 自动改 |

**Semantic Memory 里按场景的激进程度**：

| 场景 | 策略 | 原因 |
|---|---|---|
| 电商偏好 | 激进 Supersede | 旧偏好直接作废 |
| 医疗健康 | 永不删除 + validity window | 合规审计要求 |
| 金融 CRM | Supersede + 完整归档 | 合规需留旧值 |
| Coding Agent | Supersede + 提示用户确认 | 改规则影响项目 |

**生产 AUDN prompt 的关键一行**：`"注意区分'陈述事实'和'表达意图/计划'"` —— 这是解决 Day 5 灰色地带的核心 prompt 工程。

### 追问 Q3-2：AUDN 操作的是情景记忆还是语义记忆？

**同一句话会同时产生两种写入**：

```
用户："我已经搬到巴黎了"
    │
    ├──→ Episodic：记录事件（永远 Add）
    │    "2026-04-30 用户说了'已搬到巴黎'"
    │
    └──→ Semantic：提炼事实（走 AUDN 仲裁）
         "用户当前住址 = 巴黎"（Supersede 掉"住伦敦"）
```

Episodic 是事件日志（append-only），Semantic 是当前真相（AUDN 维护）。

### 追问 Q4：Mem0 了解

**Mem0 的核心能力在 Semantic Memory**（自动从对话中抽取事实、去重、消解矛盾）。
Episodic 有基本支持（session 级对话历史），但非强项。Temporal reasoning 较弱（不像 Zep 有 validity window）。

**Mem0 本质**：帮你把"LLM 抽取 + AUDN 仲裁 + 向量存储"封装成一行代码。学完底层实现后再看 Mem0，就是"哦，它把我手写的那些逻辑封装了一层"。

**学生决定**：后续增加一节单独实践 Mem0 的 Semantic Memory + Hybrid Retrieval 能力，Episodic 不用 Mem0 实现。

### 04 实现前追问：Embedding / BM25 / RRF 概念深挖

> 2026-05-04

#### Q：Embedding 模型和搜索场景的 query rewrite 是同一个东西吗？

**不一样，但容易混**。

| | query rewrite | Embedding |
|---|---|---|
| **目的** | 把用户的自然语言改写成更好检索的形式（扩展词、消歧） | 把文本映射成向量，让语义近的文本距离近 |
| **产物** | 新的文本字符串 | 浮点数组（向量） |
| **时机** | 检索之前（pre-processing） | 检索时（计算相似度） |
| **类比** | 把"帮我找辆跑得快的车"改写为"高性能汽车" | 把"高性能汽车"变成坐标，和"超跑"坐标挨着 |

Embedding 解决的是"语义相近的文本，如何用数学方式量化距离"；query rewrite 解决的是"用户表达不准确，如何改造 query"。生产里两者常叠加使用。

#### Q：语义检索的核心价值是什么？

**核心价值**：用户用自然语言随便问，系统能自动从一堆记忆里找到语义相关的。不需要预知 key，不需要设计 filter 字段，只要"意思相近"就能命中。

这解决了纯 KV Store 的根本局限——`store.get(namespace, key)` 要求你预先知道 key 叫什么，但真实场景里用户发来的是自然语言，你根本不知道要 get 哪个 key。

#### Q：BM25 优缺点 / 擅长场景

**优点**：
- 精确实体名命中能力强（订单号、变量名、版本号等）
- 30 年工业实践验证，Elasticsearch / Lucene 默认算法
- 无需 GPU，计算轻量，低延迟
- 可解释性强（能看到哪个词贡献了多少分）

**缺点**：
- 词袋模型，不理解语义（"汽车"和"轿车"在 BM25 看来是两个词）
- 依赖语言特定的分词器（中英文需要不同处理）
- 词汇不匹配就召回失败（用户用了同义词就 miss）

**擅长场景**：
- 有精确实体名的查询（订单 ID、错误码、函数名、型号）
- 技术文档检索（关键词本身就是答案）
- 作为 Hybrid 中的"精确路"，和向量路互补

#### Q：RRF 优缺点 / 擅长场景

**优点**：
- 只用排名，不用原始分数 → 尺度无关，BM25 分和余弦分可以直接融合
- 无需训练数据，零标注成本
- 对 outlier 不敏感（一条异常高分不会掌控结果）
- 实现极简（十行代码），论文中 k=60 在大量场景下稳定有效

**缺点**：
- 当某一路完全无效时（所有文档分为 0，随机排序），噪声会干扰另一路的正确结果
  - 实测案例：查"用户喜欢什么运动品牌"，BM25 无关键词全部 score=0 → 随机排序参与 RRF → 正确的向量结果被稀释，错误结果排上去
  - 生产解法：**加权 RRF**（向量路权重更高）或**条件 fallback**（BM25 最高分为 0 时纯向量兜底）

**擅长场景**：
- 融合异构检索系统（BM25 + 向量，或多个向量模型）
- 不想做标注训练的工程团队
- 实时检索（无需离线训练，直接用）

#### Q：Elasticsearch 是不是内置了 BM25 + RRF？后续能在 08 里实践吗？

**Elasticsearch 的内置能力**：
- BM25：默认检索算法，内置
- 向量检索（kNN）：8.x+ 支持
- RRF：8.14+ **原生内置**，一个 API 调用完成

**08 的决策**：不把 Elasticsearch 放进 08。

原因：Elasticsearch 是完全独立的搜索引擎体系，引入后需要单独学一套 API（索引、mapping、查询 DSL）。08 的主题是"Agent 记忆架构"，把两个主题混在一起反而都学不深。

**安排**：
- 08 用 **PostgresStore + pgvector**（向量）+ **Mem0**（内置 Hybrid，封装了 BM25+RRF）
- Elasticsearch 留到 **RAG 章节**（文档问答 / 知识库检索），那才是 ES 的主场

### 05 实现后考察：03-05 综合掌握验证

> 2026-05-08

#### Q1：store.search(query) vs store.get(key)

**学生回答**：search 是语义检索，适合模糊和自然语言查询；get 是精确检索，已知 key 时使用。Store 配置 IndexConfig 后，写入时会自动通过 embedding 模型对指定 field 做向量化，search 时自动计算余弦相似度。两者搭配使用。

**老师补充**：
- `fields: ["content"]` 指定只取 value 里的 `content` 字段做 embed；不配 fields 时默认整个 value 序列化后 embed（质量差）
- `item.score` 是 search 自动返回的相似度分数，无需手动计算
- 生产里常见用法：value 里存多个字段（时间戳、分类、原文本），但只对 `summary` 或 `content` 做 embed

#### Q2：纯向量的失败场景 + BM25/RRF 角色

**学生回答**：精确实体名（ORD-123 无法区分）；技术术语（最准确结果不一定排最前面）。BM25 是关键词召回路，RRF 是融合排名算法，不需要归一化原始分数。

**老师补充**：技术术语失败的本质 → embedding 模型看的是"语义主题"（数据库相关），区分不了"这个词必须精确出现"。

#### Q3：Update vs Delete+Add

**学生回答**：操作的 key 不同。

**老师纠偏**：核心区别不在 key 数量（Delete+Add 可以只操作一个 key），而在**语义和原子性**：
- Update = 同 key，值变了，单步操作
- Delete+Add = 概念失效 + 新概念产生（可以是同 key 也可以不同 key）
- 生产倾向用 Update：原子性更好，Delete+Add 中间崩溃会留"已删未写"空洞
- 通过 prompt 规则控制："同一语义槽优先 update"

#### Q4：Demo 5 的 Delete+Add 是否合理

**学生回答**：理论上可以但不应该，可通过 prompt 控制为 update。

**老师补充**：正确。加一条 prompt 规则即可："同一语义槽（城市、职业、爱好）优先 update，减少写操作次数"。

#### Q5：AUDN Gate 放在回复之前会怎样

**学生未作答，老师补充**：
1. 用户等待时间变长（额外的语义检索 + LLM 仲裁延迟）
2. 写入结果本次对话根本用不到（下次对话才生效），阻塞无意义
→ 这就是 Hot/Cold 分离的核心动机

### 行业深度补充：Episodic 与 Semantic Memory 的精细处理

> 2026-05-26 补充

---

#### 一、分开存储是行业共识

Episodic Memory 和 Semantic Memory 必须用不同的存储结构、不同的写入策略、不同的检索逻辑：

| 对比维度 | Episodic（事件流） | Semantic（稳定事实） |
|---------|-------------------|---------------------|
| 写入策略 | Append-only，永不修改 | AUDN 仲裁（去重、消解矛盾） |
| 数据格式 | 带时间戳的结构化事件 | 不带时间的 KV / 向量 |
| 检索方式 | 按时间 + 关键词（最近 N 条 / 相关事件） | 按语义相似度 |
| 生命周期 | 可设 TTL 过期归档，或 Compaction 压缩 | 除非显式撤销，否则永久有效 |
| 数据量 | 大（每次交互都产生） | 小（只保留当前真相） |

混在一个表里会导致：事件把偏好淹没（检索时偏好被挤出 top-k），或偏好拖慢事件检索。

---

#### 二、Semantic Memory 从 Episodic 中提炼而来

Episodic 是原始信号，Semantic 是从信号中提炼的稳定结论。一条用户消息可以同时产生两种写入：

```
用户行为事件流：
  购买 Nike Air Max → 购买 Nike Pegasus → 退货 Adidas Ultraboost → 浏览 Nike Dunk

                    ↓ 提炼（LLM 语义理解 + Evidence 累积）

Semantic 结论：
  brand_preference = Nike (strength=3, evidence=[evt-1, evt-2, evt-4])
  brand_negative = Adidas (strength=1, evidence=[evt-3])
  category_preference = 跑鞋 (strength=4)
```

提炼不是简单的计数规则。行业实际用 LLM 理解事件语义（"退货"和"购买"对 brand_preference 的影响方向相反），并为每条偏好维护 **strength（强度）** 和 **evidence（证据链）**。

MARS 论文（2025）定义了 6 种生命周期操作：

| 操作 | 触发条件 | 效果 |
|------|---------|------|
| Extraction | 积累了一定量新事件 | 从事件中提取新偏好 |
| Reinforcement | 新证据支持已有偏好 | strength + 1 |
| Weakening | 新证据反对已有偏好 | strength - 1 |
| Consolidation | 检测到语义重复条目 | 合并同类偏好 |
| Evidence-driven Forgetting | 长期无新证据 | 渐衰（降低检索排名，不删除） |
| Profile Resynthesis | 偏好变动后 | 重新生成自然语言摘要 |

三层分类的根源是认知科学 Soar 架构（1983）→ CoALA 论文（Princeton 2023）正式迁移到 LLM Agent 领域。MARS 是在推荐系统场景做了更精细的拆分（Event / Preference / Profile），更被广泛认可的通用分类仍然是 CoALA 的 Working / Episodic / Semantic / Procedural 四层。

---

#### 三、检索优先级：多维度加权排序

行业标准起点是 Stanford Generative Agents（2023，引用 3000+）定义的三维模型：

```
retrieval_score = α × Recency + β × Relevance + γ × Importance
```

**Recency（时间衰减）**

记忆距离上次被访问越久，分数越低。实现为指数衰减：

```
recency_weight = exp(-λ × days_since_last_access)
```

不同类型的记忆衰减速率不同（tier-aware）：

| 记忆类型 | λ 值 | 半衰期 | 设计意图 |
|---------|------|--------|---------|
| 原始事件 | 0.04 | 17 天 | 单次事件快速淡出 |
| 周摘要 | 0.015 | 46 天 | 经过验证的模式持续更久 |
| 月摘要 | 0.005 | 138 天 | 稳定长期模式几乎不衰减 |
| 规则/指令 | 0 | 永不 | Procedural Memory 不衰减 |

**Relevance（语义相关）**

和当前 query 的 cosine similarity。这是基础维度，所有系统必备。

**Importance（重要性）**

记忆本身的固有重要性，和当前 query 无关：
- 用户显式指令（"以后别推 Adidas"）→ 高 importance
- 行为推断（浏览了一次 Adidas）→ 低 importance
- Generative Agents 用 LLM 打 1-10 分

**Frequency（频率）**

被多次提及或访问的记忆获得加权。Zep 实现为 episode-mentions reranker——在对话中被频繁引用的实体排名更高。

**Tier Boost（层级加权）**

经过 Compaction 压缩的摘要比原始事件权重更高（1.2x）。洞察：能被聚合 = 反复出现的模式 = 比单次事件更可信。

**不同业务场景的权重配置**：

| 场景 | Recency | Relevance | Importance | 原因 |
|------|---------|-----------|------------|------|
| 客服 | 0.3 | 0.3 | 0.4 | 账户信息和政策必须可靠出现 |
| 研究助手 | 0.1 | 0.6 | 0.3 | 用户在搜索特定知识 |
| 个人助理 | 0.4 | 0.3 | 0.3 | 通常问最近的事 |
| 电商推荐 | 0.3 | 0.4 | 0.3 | 当前意图决定推荐方向 |

**关键设计原则**：衰减的是检索优先级，不是删除数据。低分记忆排不到 top-k 但仍然存在，未来被重新提及时可"复活"。

---

#### 四、冲突处理机制

**冲突类型 1：行为事件之间矛盾**

处理方式是 evidence 累积而非覆盖。"购买 Nike"给 brand_preference(Nike) 的 strength +1，"退货 Nike"给 strength -1。最终 strength 是所有相关证据的净效果。

**冲突类型 2：对话表态 vs 行为统计**

对话中的明确表态被视为强证据（weight 高于普通行为事件），可以一次性大幅改变 strength。但仍然不是"立刻删除"，而是量化的权重变化。

**冲突类型 3：短期意图 vs 长期偏好**

这不是冲突。"帮我找双皮鞋参加晚宴"是当前意图（来自对话 context），"喜欢运动鞋"是长期偏好（来自 Semantic Memory）。两者在不同层级共存，当前意图决定本次推荐方向，长期偏好影响细节。

---

#### 五、行业关键方案

**1. Reflection（Stanford Generative Agents 2023）**

定期让 LLM 对近期记忆做反思，提炼高阶结论写回记忆流：

- 触发条件：最近事件的 importance 分数累计超过阈值（论文中为 150）
- 过程：取最近 100 条记忆 → LLM 生成 3 个高层问题 → 检索相关记忆 → 提炼 insight
- Reflection 结果作为新记忆写回流，下次检索可直接命中高阶结论
- 支持递归：对 Reflection 再做 Reflection，形成抽象层次树

**2. Validity Window（Zep/Graphiti 2024-2025）**

每条 fact 用双时态模型（bi-temporal）标注：

| 字段 | 含义 |
|------|------|
| valid_at | 事实在现实世界开始为真的时间 |
| invalid_at | 事实在现实世界停止为真的时间（null = 仍有效） |
| created_at | 系统何时知道这个事实 |
| expired_at | 这条记录何时被新信息替代 |

查询"用户 2025 年 3 月住哪"→ 匹配 `valid_at <= 2025-03 AND (invalid_at > 2025-03 OR invalid_at IS NULL)`。旧 fact 不删除，只标记 invalid_at，完整保留演变历史。

用途：金融合规（"这笔交易时客户地址是什么"）、医疗、CRM。

**3. Gated Write（CraniMem 2025）**

比 AUDN 更前置的写入过滤——输入到达时先做 gate，决定"是否值得进入记忆处理流程"：

```
输入 → 相关性 gate（和当前 goal 相关吗？Sim(input, goal) < τ_noise → 丢弃）
     → Utility scoring（importance × surprise × emotion）
     → 只有 score > threshold 才进入后续的提取和存储流程
```

实测比 Mem0 抗噪能力更强。适合噪音多的场景（如客服对话中大量寒暄）。

**4. Uncertainty-gated Read（OBLIVION 2025）**

大多数系统每轮对话都检索记忆。OBLIVION 的洞察：如果 Agent 对当前回答很确定，检索是浪费。

```
Agent confidence > threshold → 直接回答，跳过记忆检索
Agent confidence < threshold → 触发检索
```

减少约 40% 的无效检索调用，降低延迟和成本。

**5. Cross-encoder Rerank**

粗排（BM25 + 向量 + RRF）取 top-50 → Cross-encoder 精排模型逐对评估 (query, memory) → 重排为 top-5。

Zep 实测：加精排后准确率 89% → 94.8%，代价是增加延迟。

| **SqliteSaver** | LangGraph 内置 | SQLite 文件 | 单机原型 | 写锁数据库级，并发瓶颈 |
| **PostgresSaver** | `@langchain/langgraph-checkpoint-postgres` | Postgres 表 | **生产** | 行级锁，支持并发；JS/TS SDK 天然异步 |
| **MongoDBSaver** | `@langchain/langgraph-checkpoint-mongodb` | MongoDB | 生产（已用 Mongo 的团队） | 文档型，适合非关系型偏好 |

### 2. Long-term Store（Semantic / Episodic 持久层）

| 组件 | 类型 | 底层存储 | 语义检索 | 适用阶段 | 备注 |
|---|---|---|---|---|---|
| **InMemoryStore** | LangGraph 内置 | JS Map | ✅（需配置 IndexConfig） | 开发/测试 | 配置 `{ index: { dims, embeddings } }` 后支持向量检索 |
| **PostgresStore** | `@langchain/langgraph-store-postgres` | Postgres + pgvector | ✅ | **生产** | namespace 隔离，内置向量检索 |

### 3. 专用记忆框架（Drop-in Memory Layer）

| 框架 | 核心能力 | 优势 | 劣势 | 适用场景 |
|---|---|---|---|---|
| **Mem0** | Semantic Memory 自动抽取 + AUDN + 向量/图存储 | 1 行集成，21 个框架适配 | 图记忆仅 Pro（$249/月），时态推理弱 | 快速上线，偏好/事实管理 |
| **Zep / Graphiti** | 双时态知识图谱（validity window） | 时态推理强，适合"什么时候是真的" | p95 ~4s，延迟较高 | CRM、医疗、金融合规 |
| **Letta (MemGPT)** | Agent Runtime + 三层记忆（Core/Recall/Archival） | LLM 自主管理记忆 | 锁定严重，换走等于重写 | 需要 Agent 自治管理记忆 |
| **OMEGA** | 长会话记忆优化 | LongMemEval 95.4%（SOTA） | 学术阶段，未量产 | 研究/对标 |

### 4. 检索策略组件

| 策略 | 实现方式 | 解决什么问题 | 备注 |
|---|---|---|---|
| **BM25** | 关键词倒排索引（Elasticsearch / Tantivy / 手写） | 精确实体匹配（订单号、变量名） | 语义理解弱 |
| **Vector Search** | Embedding + ANN（pgvector / Pinecone / Qdrant） | 语义相似度 | 精确名词易混淆 |
| **Hybrid (BM25 + Vector + RRF)** | 两路召回 + Reciprocal Rank Fusion | **生产标配**，比纯向量 recall 高 15-30% | Mem0 / Zep 内置 |
| **Cross-encoder Rerank** | 精排模型（Cohere / BGE Reranker） | 粗排后精排，提升 precision | 增加延迟，适合对精度要求高的场景 |
| **Graph Traversal** | 知识图谱多跳查询 | 关系推理（"Alice 和 Bob 合作过什么"） | 需要图数据库（Neo4j / Zep） |

### 5. 写入策略组件

| 策略 | 适用记忆类型 | 核心逻辑 | 备注 |
|---|---|---|---|
| **Append-only** | Episodic | 事件日志，只增不改 | 简单但长期会膨胀 |
| **AUDN Curation Gate** | Semantic | LLM 仲裁 Add/Update/Delete/Noop | Mem0 内置，LangGraph 需自建 |
| **版本控制 + 人工审核** | Procedural | 规则变更影响面大 | AGENTS.md / CLAUDE.md 走 git |

### 6. 架构模式

| 模式 | 描述 | 组件 | 适用 |
|---|---|---|---|
| **Hot/Cold Path 分离** | 读同步、写异步（队列） | Redis Streams / Kafka + Worker | 所有生产系统 |
| **滑动窗口 + 摘要** | 近期消息保留原文，远期压缩为摘要 | LLM summarization | 长对话场景 |
| **Namespace 隔离** | `thread_id` 隔离短期，`user_id` 隔离长期 | LangGraph Store namespace | 多租户必备 |
| **PII 脱敏** | 写入前过滤个人信息 | Presidio / 正则 / LLM 抽取 | GDPR / AI Act 合规 |

### 7. Procedural Memory 标准

| 标准 | 所属产品 | 特点 |
|---|---|---|
| **AGENTS.md** | 跨工具开放标准 | Cursor、Codex、GitHub Copilot 共读 |
| **CLAUDE.md** | Anthropic 专有 | 层级加载（user → project → local），支持 `@imports` |
| **MEMORY.md** | Claude Code auto-memory | Agent 自己学到的写自己（200 行 / 25KB 上限） |
| **.cursor/rules/** | Cursor | 项目/目录级规则（`.cursorrules` 已弃用），Cursor 专有格式 |
